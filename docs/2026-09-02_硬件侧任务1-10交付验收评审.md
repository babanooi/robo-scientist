## 4. 必须先解决的技术阻塞

### 4.1 bridge 不能直接接入当前上层

当前项目合同位于 `roboscientist/hardware_bridge/BACKEND_CONTRACT.md`，上层预期的是：

```text
GET  /health
GET  /state
POST /preflight
POST /execute_pick_place
POST /stop
```

归档中的 `bridge_v2.py`：

- `import bridge as v1`，但归档没有 `bridge.py`；
- 其它核心路由依赖 v1 模块，无法独立启动；
- 默认绑定 `127.0.0.1`，远程上层电脑无法直接访问；
- 使用旧式 `mode/parameters` 设计，与当前 `execute_pick_place` 合同不一致。

硬件侧应提供完整可运行 bridge，或在 ArmPi 主机部署一个适配层，把 ArmPi 的内部调用映射到当前项目合同。不得让上层直接发布 ROS 动作或舵机指令。

### 4.2 “说明脚本”与“最终源码”不一致

`baseline_promotion_fix_reference.py` 描述了候选状态、基线晋级和校验逻辑，但实际归档的 `build_safety_profile.py`、`safety_wrapper_common.py` 没有对应实现。请硬件侧提供最终版本源码/commit 和哈希，明确哪些文件是真正运行过的版本；不能用 reference 说明代替实现。

### 4.3 评价结果必须由实机证据产生

动作函数返回成功不等于抓取、抬升、放置成功。每轮实验至少需要：

```text
experiment_id
实际计划与参数
bridge_result
视觉 evaluation
before / grasp_lift / after 证据
关节轨迹与事件日志
标定版本
```

这样上层 Qwen 才能基于失败原因提出受限 P1，而不是根据人工描述或一次性截图猜测。

## 6. 补交后的验收顺序

1. 在 ArmPi 主机启动 bridge，先完成无动作 `/health`、`/state`、`/preflight` 联调；
2. 用三条非空定位样例核对目标颜色、坐标系、单位和标定版本；
3. 执行一次动作中 Stop，确认停止回执和机械臂不再续动；
4. 导出成功 P0 包，检查 `experiment_id`、参数、轨迹、评价和图像能互相对应；
5. 在相同场景获得真实失败 P0 后，再生成单参数 P1 候选；
6. 执行 P1 同场景复验并导出比较结果；
7. 软件侧接入前端实时状态、轨迹和 P0/P1 证据展示。

## 7. 软件侧当前可做与不可做

### 现在可以做

- 静态审查源码和 SHA256；
- 按当前项目合同准备 bridge 客户端和安全预检 UI；
- 用离线数据搭建结果卡片、轨迹对比和 Qwen 反馈流程；
- 为硬件补交包准备自动校验脚本。

### 现在不能可靠做

- 直接从上层电脑启动或控制这份 `bridge_v2.py`；
- 证明 Stop 已真实接管机械臂；
- 证明视觉评价识别了红色目标并放入 B 区；
- 证明 P0 失败 → P1 候选 → P1 成功的真实迭代效果；
- 将 DOCX 中的 `COMPLETE` 直接作为比赛验收证据。

## 8. 最终完成定义

只有当以下链路在同一组可追溯实验数据中闭合，任务 1–10 才可标记为通过：

```text
任务输入
→ Qwen 生成受约束计划
→ 真实视觉定位
→ 安全预检
→ P0 实机执行
→ 视觉评价与证据归档
→ Qwen 分析失败原因
→ 只改一个参数族的 P1 候选
→ 同场景 P1 实机复验
→ 前端展示参数、轨迹、结果和证据
```

安全层必须独立于 Qwen：模型不能直接输出舵机 ID、脉宽、ROS 动作或 shell 命令，也不能绕过工作空间、速度、超时和停止机制。
