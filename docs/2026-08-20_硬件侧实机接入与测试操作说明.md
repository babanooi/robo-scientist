# ArmPi Ultra 实机接入与测试操作说明

日期：2026-08-20
适用场景：固定工作台，红色长方体 A 点抓取并放置到 B 点
软件交付分支：`codex/real-arm-closed-loop`
应用代码基线提交：`a2f8abb0ebc2f2dc399869bf1b324b6fc074b2c4`

> 本文是硬件组现场操作手册。完整字段合同、验收边界和证据要求以[硬件组 GitHub 拉取与实机闭环验收](2026-08-20_硬件组GitHub拉取与实机闭环验收.md)为准；二者不一致时，以后者为准。

## 1. 目标与边界

本次接入要证明的链路是：

```text
浏览器/API（8001）
  -> RoboScientist 上层安全检查与实验归档
  -> ArmPi HTTP bridge（8060）
  -> 已验证的高层 wrapper
  -> ROS 2 / 厂商控制程序 / ArmPi 实机
  -> 视觉评估器写入 evaluation.json
  -> 上层归因、生成一个候选 P1、同条件复验
```

上层应用**不直接控制舵机 ID、脉冲值或 ROS topic**。硬件组保持厂商代码和已验证运动脚本的所有权，只通过 bridge 接收经过安全检查的 JSON 计划。

以下结论必须分开记录：

| 结论 | 需要什么证据 | 不能据此宣称什么 |
|---|---|---|
| 已连通 | `/health`、`/api/runtime?mode=real_arm`、无动作预检通过 | 不能证明机械臂抓取成功 |
| P0 实机基线已验证 | P0 wrapper 日志、视觉 `evaluation.json`、图像/视频 | 不能证明发生了反馈优化 |
| P0 -> P1 候选闭环已验证 | 两轮独立实机证据、带方向失败残差、参数 SHA256 回显 | 单次 P1 不代表 Skill 已晋升或成功率提高 |

**当前代码可用于实机联调，但不提供人为造错功能。** 如果 P0 正常成功，系统会停止而不生成 P1，这是正确结果。若需要展示反馈迭代，硬件组必须先提交一份经安全负责人批准的“可复现 P0 失败条件”说明，或等待实际观测到可归因的失败；不得伪造 `evaluation.json`、手动改写结果或放宽安全边界来制造 P1。

## 2. 现场角色与停止规则

| 角色 | 现场责任 | 没有完成时的处理 |
|---|---|---|
| A：设备与部署 | 拉取代码、配置 Python/ROS、启动 bridge 和网页服务 | 不进入任何 P0 动作 |
| B：运动与安全 | 清场、检查急停、审核工作空间/速度、现场监护和接管 | 任一不确定项即停止 |
| C：视觉评估 | 启动相机/视觉进程，按实验 ID 生成真实评价和图像/视频 | 不运行官方 P0/P1 闭环 |
| D：标定与参数映射 | 核对标定、目标/B 点、P1 高层参数映射和单次偏移位置 | 禁止自动生成位置补偿 P1 |
| E：实验与证据 | 保存命令输出、实验目录、日志、时间线和异常记录 | 不得宣布验证完成 |

开始运动前，B 必须确认：

1. 机械臂周围已清场，机械臂、夹爪、线缆和相机无遮挡、无松动；
2. 物理急停已知、可触及并可用；
3. 现场人员明确谁负责观察、谁负责急停、谁负责操作网页；
4. A 已完成本文件第 7 节的无动作检查，输出包含 `RESULT: ready for supervised P0`；
5. 任意人发现异常轨迹、接触风险、视觉误识别、停止接口失败或数据不一致时，立即点击网页“停止 / 接管”；若没有明确的停止成功回执，立即使用物理急停。

不要把 `pick_place_sequence_completed` 当成抓取成功。它只说明 wrapper 声明动作链已结束，真实抓取、抬升、运输和放置结果只能由 C 的结构化视觉结果确认。

## 3. 部署前准备

目标机器为 ArmPi 的 Ubuntu / ROS 2 Humble 主机。以下信息必须由现场填写，不要从模板或旧记录直接沿用：

| 配置项 | 现场确认内容 |
|---|---|
| `ARMPI_TASK_DIR` | 已验证 P0 脚本所在目录，预期为 `/home/ubuntu/armpi_tasks` |
| `ARMPI_WRAPPER` | 已验证 P0 入口 `run_final_dynamic_pick_place.sh` 的绝对路径 |
| `ARMPI_STOP_COMMAND` | 已实测的、能停止当前控制栈的**绝对路径命令** |
| 标定版本 | 当前相机到 `base` 坐标系标定版本，不得为空或含 `REPLACE_WITH` |
| A 点 / B 点 | 当前设备下的米制 `base` 坐标，B 点须和 P0 成功脚本一致 |
| 工作空间与速度 | 由 B 审核的最小/最大 XYZ、最高速度、最高偏移 |
| 视觉评估器 | 实际运行命令、版本号、输出图像/视频目录和成功判据 |

`ARMPI_STOP_COMMAND` 由 Python 使用参数数组执行，不经过 shell 展开。因此不能写 `~`、`&&`、管道或占位文字；应写成已经验证的绝对路径命令，例如 `/home/ubuntu/armpi_tasks/stop_robot_safely.sh`。示例仅说明格式，不能直接替换现场停止方案。

## 5. 先采集能力包，再冻结 P0 原始基线

### 5.1 只读能力包

先运行只读采集器：

```sh
cd /home/ubuntu/robo-scientist
source /opt/ros/humble/setup.bash
. .venv/bin/activate
python3 scripts/collect_armpi_capabilities.py --strict
```

采集器只读取允许清单中的源码和 ROS 2 图谱元数据，不导入硬件代码、不启动 wrapper、不发布运动命令。将其输出的 `.tar.gz`、`capability_report.json` 和完整终端文本回传软件侧。即使 `--strict` 退出码为 `2`，也必须保留该包；这表示需要先审查真实接口，不能靠猜测继续配置。

### 5.2 验证厂商 P0 成功脚本

只有 B 已完成清场和急停确认时，才可进行这一步。先运行无动作 `check`：

```sh
bash /home/ubuntu/armpi_tasks/run_final_dynamic_pick_place.sh check \
  |& tee ~/armpi_tasks/p0_baseline_check_$(date +%Y%m%d_%H%M%S).log
```

输出必须包含：

```text
STATUS: numeric_safety_passed
STATUS: preflight_passed
```

确认无误后，B 现场监护执行一次原始 P0 动作，并保存日志：

```sh
bash /home/ubuntu/armpi_tasks/run_final_dynamic_pick_place.sh pick-place \
  |& tee ~/armpi_tasks/p0_baseline_pick_place_$(date +%Y%m%d_%H%M%S).log
```

这一步的成功条件是：方块被夹住、抬起、运输中未掉落、放到 B 点，且没有触碰安全边界。若任何一项不成立，先修复厂商 P0 基线；不要把上层应用接在一个未验证的机械臂动作链上。

## 6. 配置安全档案、视觉评价与候选参数入口

### 6.1 本地实机档案

创建不提交 Git 的本地档案：

```sh
cd /home/ubuntu/robo-scientist
cp configs/real_arm_profile_template.json configs/real_arm_profile.local.json
```

由 B/D 编辑 `configs/real_arm_profile.local.json`，并逐项确认：

```json
{
  "bridge_url": "http://127.0.0.1:8060",
  "target_pose": {
    "frame_id": "base",
    "calibration_version": "当前已审核的真实版本"
  },
  "destination_pose": {
    "frame_id": "base"
  },
  "safety_constraints": {
    "profile_version": "当前已审核的安全档案版本",
    "allow_real_robot": true
  },
  "motion_enabled": true
}
```

模板里的坐标、工作空间和速度仅是结构样例，必须替换为当前设备实测值。完成后运行：

```sh
python3 -m json.tool configs/real_arm_profile.local.json >/dev/null
rg -n 'REPLACE_WITH|REPLACE WITH|替换' configs/real_arm_profile.local.json
```

第一条必须成功；第二条必须没有输出。`target_pose`、`destination_pose`、wrapper 内部 B 点三者的坐标系和数值必须一致，允许的数值误差不超过 1 mm。

### 6.2 视觉结果进程

bridge 在每次动作结束后会在本轮运行目录写入 `evaluation_request.json`，随后等待 C 的视觉进程写入同目录 `evaluation.json`。C 必须使用现有相机/识别链路生成真实结果，不能复制模板或人工猜测。

评价文件最小结构见 `configs/evaluation_result_template.json`，至少应包含：

```json
{
  "experiment_id": "与 evaluation_request.json 相同",
  "evaluator_type": "vision",
  "evaluator_version": "camera-evaluator-v1",
  "outcome": {
    "object_grasped": true,
    "object_lifted": true,
    "object_placed": true
  },
  "evidence": ["/绝对路径/本轮图像或视频"]
}
```

若出现位置偏差，必须将 `outcome.object_placed` 置为 `false`，并提供：

```json
{
  "failure_code": "POSE_OFFSET",
  "position_error_xyz_m": [0.008, -0.003, 0.000]
}
```

三轴误差必须是以当前定义坐标系表示的带符号米制值。只有误差大小、没有方向时，上层不会生成位置补偿 P1。

### 6.3 候选 P1 参数化 wrapper

仓库提供 `armpi_parameterized_runner.py`，但硬件组还必须在已验证高层控制代码之上实现：

```text
/home/ubuntu/armpi_tasks/run_roboscientist_experiment.sh
```

该脚本必须接受：

```sh
bash run_roboscientist_experiment.sh check \
  --parameters <skill_parameters.json> \
  --parameters-sha256 <64位SHA256>

bash run_roboscientist_experiment.sh pick-place \
  --parameters <skill_parameters.json> \
  --parameters-sha256 <64位SHA256>
```

它必须实际读取参数文件，在进入 IK 前的已审核高层 `base` 坐标目标上**只应用一次**候选参数，并在 `check`、`pick-place` 两次输出中都包含：

```text
STATUS: skill_parameters_applied sha256=<同一个64位SHA256>
STATUS: numeric_safety_passed
STATUS: preflight_passed
```

`pick-place` 还必须输出 `STATUS: pick_place_sequence_completed`。当前自动优化只允许一次修改一个参数族：

| 参数族 | 当前可用范围 |
|---|---|
| `grasp_offset_m` | 每轴不超过 ±0.020 m |
| `path_profile` 中的 `transit_height_m` | 0.05–0.20 m |

`approach_height_m` 和 `speed_m_s` 必须保持 P0 默认值，不能作为自动调参项。严禁把候选偏移同时施加到目标脚本、TCP 变换和底层舵机层，否则会发生重复校正。

## 7. 启动 bridge 并完成无动作预检

在终端 A 启动 bridge。以下路径和值必须替换为第 3 节已审核的真实值；所有 `ARMPI_*` 变量必须在**启动 bridge 的同一个终端**导出：

```sh
cd /home/ubuntu/robo-scientist
source /opt/ros/humble/setup.bash
. .venv/bin/activate

export ARMPI_TASK_DIR=/home/ubuntu/armpi_tasks
export ARMPI_WRAPPER=/home/ubuntu/armpi_tasks/run_final_dynamic_pick_place.sh
export ARMPI_RUN_ROOT=/home/ubuntu/armpi_tasks/roboscientist_runs
export ARMPI_EVIDENCE_DIR=/home/ubuntu/armpi_tasks
export ARMPI_STOP_COMMAND=/home/ubuntu/armpi_tasks/已实测停止脚本
export ARMPI_RESULT_EVALUATOR=roboscientist.hardware_bridge.result_file_evaluator:evaluate_result_file
export ARMPI_EVALUATION_TIMEOUT_S=60
export ARMPI_PARAMETERIZED_WRAPPER=/home/ubuntu/armpi_tasks/run_roboscientist_experiment.sh
export ARMPI_EXPERIMENT_RUNNER=armpi_parameterized_runner:run_experiment

python3 -m roboscientist.hardware_bridge.server \
  --host 0.0.0.0 --port 8060 \
  --allow-real-motion \
  --backend armpi_final_wrapper_backend:create_backend
```

`已实测停止脚本`只是醒目的占位提示，不能原样执行。bridge 启动本身不运行 `pick-place`，但已经进入可以接收真实动作请求的服务状态，因此 B 必须在场。

在终端 B 执行以下无动作检查：

```sh
cd /home/ubuntu/robo-scientist
source /opt/ros/humble/setup.bash
. .venv/bin/activate

curl -fsS http://127.0.0.1:8060/health | tee bridge_health.json
python3 scripts/verify_hardware_setup.py \
  --profile configs/real_arm_profile.local.json \
  --require-closed-loop |& tee verify_hardware_setup.log
```

该脚本会调用 bridge 的 `preflight` 和空闲态 `/stop`，但不调用 `pick-place`。只有终端最后出现：

```text
RESULT: ready for supervised P0
```

才允许进入下一节。`RESULT: blocked`、`preflight rejected`、`stop_probe` 失败、配置字段缺失或候选参数 runner 未就绪，都是停止条件。

## 8. 启动上层网页与 API

在终端 C 启动上层服务。Qwen Key 只写入当前进程环境，不写入 Git、日志截图、`evaluation.json` 或实验包：

```sh
cd /home/ubuntu/robo-scientist
source /opt/ros/humble/setup.bash
. .venv/bin/activate

export ROBO_ALLOW_REAL_ARM=1
export DASHSCOPE_API_KEY='由项目负责人在现场安全注入'
export DASHSCOPE_BASE_URL='https://dashscope.aliyuncs.com/compatible-mode/v1'
export QWEN_MODEL='qwen3.7-plus'
export QWEN_TIMEOUT_S=90

python3 -m roboscientist.web.server \
  --host 0.0.0.0 --port 8001 \
  --data-root data/real-arm-test \
  --real-arm-profile configs/real_arm_profile.local.json
```

另开终端核对服务状态并保存输出：

```sh
curl -fsS http://127.0.0.1:8001/api/config | tee api_config.json
curl -fsS 'http://127.0.0.1:8001/api/runtime?mode=real_arm' | tee api_runtime_real_arm.json
```

浏览器打开：`http://<ArmPi主机IP>:8001`。选择“Real Arm”后，页面应显示桥接、停止、结果评估、候选参数四项均为“就绪”。若 Qwen 未配置，可以做 `deterministic_only` 联调，但不能作为赛题所需的 Qwen 规划和反馈证据。

## 9. 分级测试顺序

### 9.1 L0：应用与接口，无动作

完成第 4、5.1、6、7、8 节。验收材料为代码哈希、能力包、`/health`、`/api/config`、`/api/runtime` 和 `verify_hardware_setup.log`。

### 9.2 L1：受监督 P0 实机接入

这一步先验证上层 API 到已冻结 P0 wrapper 的实际连接。B/C/D 必须在场，C 的视觉进程必须已启动。可在网页选择“仅运行 P0（诊断）”，或用以下可归档 API 请求：

```sh
curl -fsS -X POST http://127.0.0.1:8001/api/tasks \
  -H 'Content-Type: application/json' \
  -d '{
    "task_text": "把固定工作台上的红色方块放到右侧目标区域",
    "scenario": "pose_offset",
    "mode": "real_arm"
  }' | tee p0_api_response.json
```

这里的 `scenario` 在实机模式下是实验记录字段；真实目标、B 点和安全范围来自已审核的 `real_arm_profile.local.json`，不是由该字段改变。L1 使用确定性 P0，不构成 Qwen 赛题证据。

L1 通过条件：

1. 返回和 `result.json` 中 `data_source` 都是 `real_arm`；
2. wrapper `check` 与 `pick-place` 日志齐全；
3. 视觉 `evaluation.json` 的 `experiment_id` 正确、`evaluator_type=vision`、`evaluator_version` 非空，且图像/视频是可访问的绝对路径；
4. 现场观察和视觉结论一致；
5. 发生异常时，停止、人工接管和恢复记录完整。

### 9.3 L2：Qwen 规划与反馈候选验证

仅当 L1 已通过，并且存在真实、可归因、且经 B/D 允许复现的 P0 失败时，才运行这一层。典型位置偏差必须来自视觉实际测量并包含带符号 `position_error_xyz_m`。不要通过移动方块、改灯光、换相机、改标定版本或改成功判据来让 P1 看起来更好。

执行前确认：

1. P0/P1 使用同一 `scene_id`、A/B 目标、标定版本、相机/光照、评价器版本和成功判据；
2. 候选仅变更 `grasp_offset` 或 `path_profile` 其中一个参数族；
3. `run_roboscientist_experiment.sh` 已由 D 审核，能实际应用参数并回显 SHA256；
4. B 明确同意现场监督软件自动衔接候选 P1；任何人可随时停止。

官方路径通过 campaign API 运行。此请求可能在 P0 有合格失败证据后继续执行一轮候选 P1，发起前必须完成以上确认：

```sh
curl -fsS -X POST http://127.0.0.1:8001/api/campaigns \
  -H 'Content-Type: application/json' \
  -d '{
    "task_text": "把固定工作台上的红色方块放到右侧目标区域",
    "scenario": "pose_offset",
    "mode": "real_arm",
    "use_qwen": true,
    "auto_run_p1": true
  }' | tee campaign_launch_response.json
```

保存响应中的 `campaign_id`，再完整读取并归档：

```sh
curl -fsS http://127.0.0.1:8001/api/campaigns/<campaign_id> \
  | tee campaign_<campaign_id>.json
```

可能出现的正确结果：

| 返回状态 | 含义 | 下一步 |
|---|---|---|
| `campaign.decision.reason = P0 has no structured failure` | P0 已成功，无需 P1 | 记录成功基线，不强行生成 P1 |
| `campaign.decision.status = manual_review_required` | 视觉证据、同条件或安全条件不足 | 修复证据/配置后重新从 P0 开始 |
| `QWEN_PLANNING_FAILED` / `QWEN_ADJUSTMENT_FAILED` | 模型调用或结构化校验失败 | 保存失败元数据，不能静默降级 |
| `campaign.decision.status = p1_executed` | P1 候选已实际执行 | 审计第 10 节证据，仍只标记 candidate |

## 10. P0/P1 证据审计与回传

对每一轮 P0/P1，E 必须保留完整目录，通常位于：

```text
/home/ubuntu/robo-scientist/data/real-arm-test/experiments/<experiment_id>/
/home/ubuntu/armpi_tasks/roboscientist_runs/<experiment_id>/
必须回传给软件侧：

1. `git rev-parse HEAD`、能力包和完整安装/无动作检查输出；
2. bridge `/health`、网页 `/api/config`、`/api/runtime?mode=real_arm` 的完整 JSON；
3. 空闲态 stop probe 和软件停止命令的实测记录；
4. P0/P1 各自的 `plan.json`、`result.json`、`analysis.json`、wrapper `check`/`pick-place` 日志；
5. P0/P1 各自的 `evaluation_request.json`、`evaluation.json`、RGB/深度图像或视频、评估器日志；
6. P1 的 `skill_parameters.json`、SHA256、`executed_parameters` 和两次 wrapper 回显；
7. campaign JSON 及 Qwen 的 planning/adjustment 元数据；
8. 标定核验、坐标系说明、异常/拒绝/人工干预和恢复记录。

闭环候选通过审计至少应满足：

```text
P0.data_source == real_arm
P1.data_source == real_arm
P0/P1 evaluator_type == vision
P0/P1 evaluator_version 相同且非空
P1 只改一个允许参数族
P1 check 与 pick-place 回显同一个参数 SHA256
P0/P1 图像或视频各自独立存在
```

第一次 P1 仅是候选观察。项目内部建议在冻结的同条件场景下，每个版本至少独立重复 10 次后，再讨论成功率提升、Skill 晋升或回滚；这不是赛题官方固定次数。

## 11. 常见阻塞与处理

| 现象 | 首先检查 | 处理原则 |
|---|---|---|
| `/health` 显示不可用 | 路径、停止命令、backend 模块、wrapper 文件 | 修复配置，不绕过 health gate |
| `verify_hardware_setup.py` 被阻塞 | profile 占位符、空闲 stop、视觉评估器、参数 runner | 修复缺项后重跑，不执行 P0 |
| P0 wrapper 动作结束但评价失败 | C 是否按本轮 ID 写入真实 `evaluation.json`，证据路径是否存在 | 标为实机结果未验证，不由人工口头补齐 |
| P1 被拒绝 | SHA256、只改一个参数族、参数是否实际生效、同条件记录 | 修复 wrapper 映射，从新的 P0 重新开始 |
| Qwen 调用失败 | Key、模型权限、网络、结构化响应 | 保存失败证据；禁止改为假 Qwen 结果 |
| 停止接口失败 | 立即物理急停 | 后续禁止继续实验，先修复停止链路 |
