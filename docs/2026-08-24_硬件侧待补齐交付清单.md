# ArmPi Ultra 硬件侧待补齐交付清单

日期：2026-08-24
目标：让 RoboScientist 上层应用能够在固定场景（红色/彩色方块抓取并放置）完成可审计的“P0 基线实验 -> 结果获取 -> Qwen 反馈分析 -> 受限 P1 候选 -> 同条件复验”闭环。

## 1. 当前结论

硬件摸底已经证明 ArmPi 具备接入基础，不需要再提供通用使用手册或重复证明 ROS 2、相机、YOLO 是否存在。

已确认的能力如下：

| 能力 | 已确认内容 | 上层可如何使用 |
|---|---|---|
| 实时 RGB | `/depth_cam/rgb/image_raw`，约 10 Hz；`http://192.168.149.1:8080/stream_viewer?topic=/depth_cam/rgb/image_raw` | 前端实时画面 |
| RGB-D 与 YOLO | RGB、Depth、CameraInfo、`/yolo/object_detect`、`/yolo/object_image` 已定位 | 视觉定位与过程展示 |
| 坐标转换 | RGB-D `camera_xyz` 经手眼标定和当前末端位姿转换为 `robot/base XYZ` | 生成可执行抓取位姿 |
| 语音 | WonderEchoPro、ASR/TTS 源码和 ROS 2 Topic 已定位 | 后续语音指令接入 |
| 网络 | `8080` 视频、`9090` rosbridge 已运行 | 前端视频与 ROS 数据桥接 |
| 运动数据 | 已有一批 `grasp_run_20260513_123541.tar.gz` | 分析关节轨迹和目标位姿 |

现有 `grasp_run_20260513_123541.tar.gz` 是真实实机运行包，包含 10 条抓取目标事件和 77,707 行关节状态。但其 `events.csv` 没有实验结果记录、ROS bag 目录为空，不能证明某次抓取/放置是否成功，也不能作为 P0/P1 效果比较的唯一证据。

## 2. 交付优先级

| 优先级 | 交付物 | 完成后可解锁的开发 |
|---|---|---|
| P0 | 实机 HTTP bridge、停止能力和安全档案 | 上层无动作预检与受控 P0 调用 |
| P0 | 视觉定位服务和非空目标样例 | Qwen 任务计划可获取真实抓取坐标 |
| P0 | 结构化视觉评价和一次成功 P0 实验包 | 前端展示真实执行结果，闭环具有真实证据 |
| P1 | 一次可归因失败 P0 实验包 | Qwen 失败分析和单参数 P1 候选 |
| P1 | 同条件 P1 复验实验包 | 展示反馈迭代和效果对比 |
| P2 | ASR/TTS 端到端验证 | 完成语音交互入口 |

P0 是本周必须完成项。没有 P0 的前三项，上层应用只能展示 Mock/离线数据，不能声称已接入实机。

## 3. 必须交付的内容

### 3.1 ArmPi HTTP bridge 与运行说明（P0）

在 ArmPi 主机启动项目专用 bridge，建议地址为 `http://127.0.0.1:8060`。`9090` rosbridge 不能替代它：上层应用不应直接发布 ROS 动作指令。

交付：

1. bridge 源码或启动脚本，以及依赖和启动命令；
2. 每个接口的一次真实请求/响应样例（密钥、内网凭据必须删除）；
3. 下列接口合同：

```text
GET  /health
POST /preflight
POST /execute
POST /stop
GET  /result/{experiment_id}
```

验收标准：

- `/health` 返回 bridge、ROS、相机、运动 wrapper 的独立状态；
- `/preflight` 不运动，且能拒绝缺失标定、停止命令或安全档案的请求；
- `/execute` 只接受上层批准的高层计划和参数白名单，不能接受任意舵机 ID、脉宽或 shell 命令；
- `/stop` 已在真实运行中验证能停止/接管，返回明确回执；
- 每次请求均返回 `experiment_id`，后续可用 `/result/{experiment_id}` 查询；
- 提供日志文件路径、开始/结束时间、已执行参数的 SHA256 回显。

### 3.2 视觉定位服务（P0）

`/yolo/object_detect` 只提供类别、2D 框、角度和置信度；上层无法由它直接抓取。硬件侧需要封装已存在的“YOLO -> RGB-D -> 手眼标定 -> robot/base XYZ”链路。

交付：

1. 一个无动作定位入口，可为 ROS 2 service、bridge 子接口或独立命令；
2. 红色方块的至少 3 条**非空**实机返回样例；
3. 当前使用的标定文件副本或 SHA256、采集时间和已知定位误差。

最小返回合同：

```json
{
  "target_id": "uuid-or-frame-id",
  "class_name": "cuboid",
  "score": 0.95,
  "angle_deg": 12.0,
  "camera_xyz_m": [0.12, -0.03, 0.42],
  "robot_xyz_m": [0.22, -0.05, 0.03],
  "frame_id": "base",
  "calibration": {
    "file_sha256": "...",
    "captured_at": "2026-08-24T10:30:00+08:00"
  },
  "evidence_image": "/absolute/path/to/image.jpg"
}
```

验收标准：放置目标后，返回非空对象；`robot_xyz_m` 以米为单位且坐标系明确为 `base`；同一目标连续三帧的位置波动和定位误差均被记录，而不是只给一张 YOLO 标注图。

### 3.3 安全档案、运动 wrapper 和停止验证（P0）

交付：

1. 当前已验证 P0 抓取放置脚本的绝对路径、启动方式和输入参数说明；
2. 可参数化 P1 wrapper 的绝对路径和调用约定；
3. `safety_profile.json`，包含工作空间 XYZ 范围、速度/加速度上限、夹爪范围、单次超时、允许优化的参数白名单；
4. 急停/停止脚本及一次“动作中停止”的实测日志；
5. 当前 A 点、B 点及其坐标系、标定关联和容差。

验收标准：

- P1 一次只能修改一个经过批准的参数族（例如接近高度或 X/Y 偏移），不能同时修改路径、夹爪、速度和目标位姿；
- 超出安全档案的请求在执行前拒绝；
- 真实停止命令已验证，不接受 `TODO`、占位脚本或仅关闭网页进程作为停止方案；
- P0 和 P1 wrapper 都输出实际应用参数与参数摘要，防止“候选参数没有真正传到机械臂”。

### 3.4 结构化视觉评价器（P0）

这是闭环最关键的缺口。动作链结束不等于抓取成功；`evaluation.json` 必须由相机/视觉流程生成，而不是人工填写。

交付：

1. 视觉评价器源码、启动命令和版本号；
2. 每轮按 `experiment_id` 写出的 `evaluation.json`；
3. 抓取前后图像或短视频，以及文件路径；
4. P0 成功案例和失败案例各一份评价文件。

最小文件合同：

```json
{
  "experiment_id": "与执行请求一致",
  "evaluator_type": "vision",
  "evaluator_version": "camera-evaluator-v1",
  "outcome": {
    "object_grasped": true,
    "object_lifted": true,
    "object_placed": true,
    "collision": false,
    "timeout": false
  },
  "failure_code": null,
  "position_error_xyz_m": [0.0, 0.0, 0.0],
  "evidence": ["/absolute/path/before.jpg", "/absolute/path/after.jpg"]
}
```

验收标准：`experiment_id` 与 bridge 执行记录一致；成功必须同时满足抓住、抬起、放入 B 点；失败必须有结构化 `failure_code`。若是位置偏差，`position_error_xyz_m` 必须是带方向的米制三轴误差，才能由上层生成安全的 P1 偏移候选。

### 3.5 P0/P1 实验数据包（P0/P1）

沿用已有 `dataset_start.sh` / `dataset_finish.sh` / `export_dataset.sh`，但补齐结果标签与视觉证据。每次导出为一个不可覆盖的压缩包，并附 SHA256。

P0 成功包必须包含：

```text
experiment.json                 # 输入任务、场景、目标与环境条件
plan_applied.json               # P0 实际参数和 SHA256
evaluation.json                 # 视觉评价
joint_states_session.csv        # 轨迹
grasp_events_session.log        # 目标 XYZ、形状、yaw
before.jpg / after.jpg          # 或短视频
calibration.yaml + sha256
wrapper.log
```

P0 失败包必须在相同场景约束下提供同样的内容，并记录真实失败原因。不得通过伪造 `evaluation.json`、移除安全限制或制造碰撞来演示反馈迭代。

P1 复验包必须额外包含：

```text
p0_experiment_id
candidate_skill.json
candidate_parameter_sha256
same_scene_check.json
```

验收标准：P0/P1 的对象、相机、A/B 点、标定和场景条件可比较；P1 的实际参数只改动一个参数族；每一项改动能在 wrapper 回显、关节轨迹和视觉结果中互相核对。

### 3.6 语音 ASR/TTS 端到端验证（P2）

现有接口和源码已经定位，但整机重启后节点没有运行。该项不阻塞 P0/P1 实机闭环，可在运动闭环稳定后接入。

交付：

1. 语音节点启动命令与依赖；
2. 一次真实中文语音的 `/vocal_detect/asr_result` 输出；
3. 上层向 `/tts_node/tts_text` 发文字后，`/tts_node/play_finish` 回执的日志；
4. ASR 错误或空结果的处理方式。

验收标准：重启设备后可重复启动；语音识别文本可通过 bridge 传到上层，且不会绕过任务确认和安全预检触发机械臂。

## 4. 不需要再提供的内容

以下内容已在现有摸底和数据包中确认，除非版本发生变化，无需重复整理：

- 8080 视频流、9090 rosbridge 的地址和基础用途；
- RGB、Depth、CameraInfo、YOLO 的 ROS Topic 名称；
- YOLO 源码入口和字段说明；
- 手眼变换的总体链路；
- 多形状抓放及关节数据采集脚本；
- 仅包含函数列表、截图或空 YOLO 消息的说明文档。

若厂商代码升级、标定重做、相机更换或动作脚本变更，必须重新提交对应的版本/哈希和一条新实测样例。

## 5. 建议交付顺序

1. 设备与安全负责人：提交安全档案、停止验证和 P0 wrapper；
2. 视觉负责人：提交非空定位样例和 `evaluation.json`；
3. 部署负责人：启动 8060 bridge，完成无动作 `/health`、`/preflight` 联调；
4. 实验负责人：导出一次成功 P0 实验包；
5. 在获得真实可归因失败后，导出失败 P0 和 P1 复验包；
6. 语音负责人：完成 ASR/TTS 端到端验证。

硬件侧每完成一项，应在团队共享目录或 GitHub release 中提供“源码/脚本 + 实测输出 + 数据包 SHA256 + 简短复现步骤”。不要只发送截图或口头结论。

## 6. 软件侧收到交付后的动作

| 收到交付 | 软件侧立即完成的工作 |
|---|---|
| bridge 与安全档案 | 连接状态、无动作预检、停止按钮和受控执行入口 |
| 定位服务 | 实时目标卡片、坐标校验和任务计划输入 |
| `evaluation.json` | 真实结果展示、失败归因和 P1 候选生成 |
| P0/P1 实验包 | 轨迹与结果对比、证据归档、Skill 版本化 |
| ASR/TTS 验证 | 语音任务下发与执行状态播报 |

## 7. 完成定义

本阶段完成不是“机械臂能抓到方块”，而是能在相同可追溯条件下，证明以下链路：

```text
任务输入
-> Qwen 输出受约束实验计划
-> 真实视觉定位与安全预检
-> P0 实机执行
-> 真实视觉评价和证据归档
-> Qwen 分析结果并提出单参数 P1
-> P1 实机复验
-> 前端展示 P0/P1 的参数、轨迹、结果与证据
```

其中安全层独立于 Qwen：模型不能直接输出舵机命令、ROS 动作指令或绕过工作空间/停止机制。
