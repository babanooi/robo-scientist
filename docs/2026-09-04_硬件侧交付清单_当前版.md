# ArmPi Ultra 硬件侧交付清单（当前版）

版本：v2.1
日期：2026-09-04
适用项目：RoboScientist / 固定场景红色方块抓取—放置—反馈迭代

## 1. 先说结论

硬件侧目前不需要再重复整理通用使用手册。当前真正缺少的是：

> 可运行的项目接口、可复验的实机输出，以及能把 P0→失败分析→P1 复验串起来的实验工件。

已有资料已经足够软件侧做参数登记、接口适配、历史轨迹回放和 Mock 回归；但还不足以让上层电脑安全调用真实机械臂，也不足以证明真实反馈迭代已经完成。

### 1.3 本清单与当前代码的关系（必须先看）

本清单是硬件侧的**交付与验收目标**，不是对当前仓库代码已经具备实机能力的声明。当前仓库的标准库 HTTP 路由可以用于 dry-run 和接口联调，但 `armpi_final_wrapper_backend.py` 目前仍有以下待补齐项：

- `/health` 主要检查文件、可导入模块和配置，尚未主动探测 ROS、相机、运动控制器和物理急停；
- 安全约束目前来自请求，尚未由 bridge 强制加载并比较本机不可被客户端放宽的安全档案；
- `/state` 不能提供连续运动状态；
- `stop()` 尚未自动使当前授权失效并记录动作前后状态；
- bridge 尚未在 HTTP 层统一强制非空且唯一的 `experiment_id`，也尚未拒绝全部低层字段。

在上述门槛和 H-01/H-02 验收通过前，软件侧保持真实运动锁定；硬件侧不能只按现有 dry-run 路由返回“已连接”。

## 3. 详细交付要求

### H-01：项目专用 HTTP bridge（P0）

#### 硬件侧要做什么

在 ArmPi 所在电脑上部署一个项目专用 bridge，把 ROS2、厂商 SDK、运动 wrapper 和相机调用封装在 bridge 内部。上层电脑只能发送高层任务计划，不能直接发布 ROS 指令、舵机 ID、脉宽或 shell 命令。

必须使用当前项目合同中的接口名：

```text
GET  /health
GET  /state
POST /preflight
POST /execute_pick_place
POST /stop
```

不要只提供旧版 `/execute`，也不能只提供 `9090 rosbridge` 让上层直接控制机械臂。

#### 必须交付

1. bridge 源码或可审计的启动脚本；
2. 完整依赖清单、Python/ROS2 版本和启动命令；
3. bridge 监听地址、端口、防火墙和内网访问说明；
4. 五个接口各一份脱敏后的真实请求/响应样例；
5. 当前运行代码的 Git commit 和 SHA256；
6. 日志保存路径；`preflight`/`execute_pick_place` 请求携带唯一 `experiment_id` 并由 bridge/backend 原样回显的样例。`stop` 允许不带 ID，以支持未知任务或失联场景的全局安全停止；若硬件自行生成 `execution_id`，必须与 `experiment_id` 分开。

#### 通过标准

- `/health` 能分别报告 bridge、ROS、相机、标定、wrapper 和 Stop 能力；没有主动探测到的能力必须标为 `unverified`，不能仅凭文件存在返回 ready；
- `/preflight` 完全不运动，并能拒绝缺标定、越界坐标、未批准参数和未配置 Stop 的请求；
- `/execute_pick_place` 执行前再次调用 preflight；
- `/stop` 在动作执行期间仍可调用；
- 一次只允许一个运动操作，重复/并发请求有明确错误；
- 返回结果包含同一个 `experiment_id`、实际参数摘要和日志工件路径；缺失或重复 ID 必须在执行前拒绝（全局 `stop` 除外）。

### H-02：安全档案、P0/P1 wrapper 与 Stop（P0）

#### 硬件侧要做什么

把实际使用的工作空间、速度、加速度、超时、夹爪限制、A/B 点、标定版本和允许调整的参数族写入版本化安全档案。P1 只能修改一个批准的参数族。

安全档案必须由机器人本机 bridge 只读加载并作为最终裁决。上层请求里的 `safety_constraints` 只能提出更严格的限制，不能扩大工作空间、提高速度、放宽置信度或覆盖 Stop/profile；bridge 必须在 `/health`、`/preflight` 和结果中回显 `safety_profile_version` 与 `safety_profile_sha256`。

#### 必须交付

```text
safety_profile.json
safety_profile.sha256
P0 wrapper 的绝对路径、版本和启动方式
real_stop_result.json
real_stop_test.log
```

还需说明：

- A 点、B 点的坐标系和容差；
- 实际 B 点的单一真源（坐标、坐标系、容差）及其与 wrapper 环境变量/配置的对应关系。当前参考 wrapper 默认 B 点为 `(0.220, -0.080, 0.030) m`，不能把这个默认值当作现场实测值；
- `grasp_offset_m`、`approach_height_m`、`transit_height_m`、`speed_m_s` 哪些允许调整；
- wrapper 如何回显实际使用的参数；
- Stop 的软件命令、物理效果和响应时间。

#### 通过标准

- 缺少安全档案、标定或 Stop 配置时，执行前拒绝；
- 超出工作空间、速度、超时或夹爪范围时，执行前拒绝；
- 真实 Stop 必须在“动作进行中”测试，不能只关闭网页或终止 bridge 进程；
- Stop 结果至少包含停止前状态、停止后状态、响应时间和动作中断日志；Stop 成功后必须使当前 experiment 进入 `stopped`/`fault`，使旧的 preflight 授权失效，禁止自动续跑；
- 文档不能用 `TODO`、`REPLACE_WITH...` 或“人工确认”代替实测结果。

### H-03：真实视觉定位与标定（P0）

#### 硬件侧要做什么

封装完整链路：

```text
YOLO/RGB-D → 相机坐标 → 手眼标定 → base 坐标 → 上层任务计划
```

#### 必须交付

至少 3 条同一场景下的非空红色方块定位样例，每条包含：

```json
{
  "target_id": "frame-or-uuid",
  "class_name": "cuboid",
  "color": "red",
  "score": 0.95,
  "angle_deg": 12.0,
  "camera_xyz_m": [0.12, -0.03, 0.42],
  "robot_xyz_m": [0.22, -0.05, 0.03],
  "frame_id": "base",
  "calibration": {
    "file_sha256": "...",
    "version": "calib-v1",
    "captured_at": "2026-09-04T10:30:00+08:00"
  },
  "evidence_image": "/absolute/path/to/image.jpg"
}
```

同时交付：

- 标定文件副本或 SHA256；
- 坐标单位、坐标轴方向和 frame 说明；
- 连续帧位置波动、置信度和已知误差；
- 上层电脑能够访问的定位接口或命令。

#### 通过标准

- `robot_xyz_m` 必须是米制 `base` 坐标；
- 样例不能是空 Topic、只含 2D 框的截图或手填坐标；
- 坐标、图像、标定版本和采集时间能够互相对应；
- 低于置信度阈值或坐标越界时，接口应明确拒绝。

### H-04：结构化视觉评价器（P0）

#### 硬件侧要做什么

动作链完成后，使用相机或已验证的视觉流程判断：是否抓住、是否抬起、是否运输、是否放入 B 区。动作函数返回“完成”不能直接视为物理成功。

#### 必须交付

1. 评价器源码、启动命令和版本号；
2. P0 成功和失败各一份 `evaluation.json`；
3. 每轮对应的 `before.jpg`、`grasp_lift.jpg`、`after.jpg` 或短视频；
4. 失败阶段和结构化 `failure_code`；
5. 位置偏差时提供带方向的 `position_error_xyz_m`。

#### 最小结果格式

```json
{
  "experiment_id": "exp-001",
  "evaluator_type": "vision",
  "evaluator_version": "camera-evaluator-v1",
  "outcome": {
    "object_grasped": true,
    "object_lifted": true,
    "object_placed": true
  },
  "metrics": {
    "collision": false,
    "timeout": false
  },
  "failure_code": null,
  "position_error_xyz_m": [0.0, 0.0, 0.0],
  "evidence": [
    "/absolute/path/before.jpg",
    "/absolute/path/grasp_lift.jpg",
    "/absolute/path/after.jpg"
  ]
}
```

#### 通过标准

- `experiment_id` 与 bridge 及计划完全一致；
- 成功必须同时满足抓住、抬起、放置；
- 失败必须有真实可追溯的失败代码和证据；
- 自动 P0→P1 和比赛成功证据必须使用 `evaluator_type="vision"`、版本号和实际图片/视频；`manual` 或 `hybrid` 只能标为 `supervised/manual_review`，不能作为自动闭环成功证据；
- 视觉评价必须有版本号和实际图片/视频，不接受空路径或人工口头结论；
- 位置偏差必须是有方向的三轴误差，不能只给一个无方向的标量。

### H-05：完整成功 P0 实验包（P0）

#### 必须交付

```text
success_p0_<experiment_id>/
  experiment.json
  plan_applied.json
  preflight.json
  bridge_result.json
  evaluation.json
  before.jpg
  grasp_lift.jpg
  after.jpg
  joint_states_session.csv
  grasp_events_session.log
  wrapper.log
  calibration/
  runtime_manifest.json
  SHA256SUMS.txt
```

`runtime_manifest.json` 至少记录：设备型号、主机环境、源码 commit、实验 ID、采集时间、场景 ID、标定版本、评价器版本和复现命令。敏感凭据、API Key 和密码不得放入包内。

#### 通过标准

所有文件必须属于同一次实验，实验 ID、参数、时间和 SHA256 能互相核对。只有校验器返回 `passed`，该包才可作为成功 P0 证据。

### H-06：真实失败 P0 实验包（P1 前置）

在与成功 P0 相同的场景、相机、A/B 点、标定和评价口径下，提供一次自然产生或可明确归因的失败 P0。不得通过伪造 JSON、移除安全限制或制造危险动作来“制造失败”。

除 H-05 的全部文件外，必须让 `evaluation.json` 明确记录失败阶段、失败代码和残差，例如 `GRASP_FAILED`、`PATH_BLOCKED` 或 `POSE_OFFSET`。

### H-07：参数化 P1 候选与同条件复验（P1）

#### 硬件侧要做什么

提供真正接受上层候选参数的 wrapper，并回显实际应用的 canonical 参数和 SHA256。当前冻结 P0 wrapper 只支持基线版本，不能直接证明 P1 已可执行。

#### P1 额外交付

P1 参数化 wrapper 的绝对路径、版本、启动方式和依赖；它不是 H-02 的 P0 通过前置条件，但在 H-07 验收前必须补齐。

#### 必须交付

P1 实验包**继承 H-05 的全部实验工件**，再增加以下 P1 专属文件；不得只交一个候选 JSON：

```text
p1_<experiment_id>/
  p0_experiment_id.txt
  candidate_skill.json
  candidate_parameter_sha256.txt
  same_scene_check.json
  preflight.json
  bridge_result.json
  evaluation.json
  comparison.json
  before.jpg
  grasp_lift.jpg
  after.jpg
  joint_states_session.csv
  grasp_events_session.log
  wrapper.log
  calibration/
  runtime_manifest.json
  SHA256SUMS.txt
```

#### 通过标准

- P1 只修改一个批准的参数族；
- P0/P1 的目标、场景、A/B 点、标定、评价器版本和成功标准一致；
- wrapper 的回显参数与 `candidate_skill.json`、SHA256 完全一致；
- P1 结果由真实评价器产生；
- `comparison.json` 同时报告结果指标和条件一致性；
- 当前唯一 canonical 参数 schema 是 `grasp_offset_m`、`approach_height_m`、`transit_height_m`、`speed_m_s` 四个键；任务 1–10 源码中只修改 `target_xyz` 的旧版候选格式必须在硬件侧适配后才能使用，不能与本 schema 并列交付；
- `grasp_offset_m` 必须明确相对于 `base` frame 的正负方向和单位；当前允许的路径族实际对应 `transit_height_m`，不能笼统写成未定义的 `path_profile`；
- 一次 P1 只能作为候选观察，不能直接宣称成功率提升。项目建议每个版本至少完成 10 次独立重复后再做性能结论。

### H-08：实时相机流（P2，可后置）

交付上层电脑可访问的 `stream_url`、协议/编码、分辨率、帧率、帧时间戳、启动命令和断流恢复方式。实时视频只用于操作监看和前端演示；它不能代替 `evaluation.json`、三阶段图片或实验 ID 对应的证据。

### H-09：ASR/TTS（P2，可后置）

交付语音节点启动命令、一次真实中文 ASR 输出、TTS 播放完成回执和空结果处理方式。语音输入必须先进入任务解析和安全预检，不能直接绕过上层控制台触发运动。

## 5. 硬件侧实际执行顺序

1. 拉取软件仓库并记录 commit；
2. 只启动 dry-run bridge，验证接口和响应格式；
3. 在无动作条件下完成真实 bridge `/health`、`/state`、`/preflight`；
4. 完成 Stop 空闲调用，再完成一次动作中 Stop 实测；
5. 采集 3 条红色方块定位样例并固定标定版本；
6. 执行并归档成功 P0；
7. 在相同条件下归档真实失败 P0；
8. 让参数化 wrapper 接受一个参数族，生成并执行 P1；
9. 导出 P0/P1 对比和 SHA256；路径长度只能在有实测 TCP/TF 轨迹时填写，否则写 `unknown`，不得用估算值；
10. 将完整压缩包和终端输出交给软件侧验收。

- [ ] `/preflight` 不会使机械臂运动；
- [ ] `/stop` 已在动作进行中实测；
- [ ] 有最终安全档案和 SHA256；
- [ ] 有 3 条非空红色目标 `base` 坐标样例；
- [ ] 有成功 P0、失败 P0 和 P1 的结构化评价；
- [ ] 三阶段图片/视频真实存在且与实验 ID 对应；
- [ ] 如交付实时视频，`stream_url` 能被上层电脑访问，帧时间戳和断流状态可见；
- [ ] P1 只改变一个参数族；
- [ ] 所有工件已写入 SHA256 清单；
- [ ] 包内没有 API Key、密码或私钥；
- [ ] 已提供复现命令、环境版本和源码 commit。

## 7. 软件侧收到交付后的处理

软件侧会按以下顺序验收，不会因“脚本退出码为 0”直接放行：

1. 校验压缩包安全性和 SHA256；
2. 检查 bridge 合同和无动作预检；
3. 核对定位坐标、标定版本和实验 ID；
4. 检查评价 JSON 与阶段图片；
5. 核对 P0/P1 参数是否只改一个族；
6. 通过后才接入前端实时状态、结果卡片和反馈迭代展示；
7. 在完整证据包通过前，真实机械臂运动开关保持锁定。

## 8. 五名研究生的建议责任边界

为避免“每个人都跑过一次但没人对交付负责”，建议按交付物设唯一主责人；其他成员可以协助，但由主责人对文档、样例和复现命令完整性负责。

| 角色 | 主责交付 | 必须交给上层软件的结果 |
|---|---|---|
| 硬件生 1：Bridge/部署 | H-01；网络、依赖、启动脚本、五个接口样例 | 可从另一台电脑访问的 URL、请求/响应样例、commit、日志位置 |
| 硬件生 2：安全与运动 | H-02；安全 profile、P0 wrapper、动作中 Stop；协同 H-07 参数化 wrapper | profile 版本/hash、A/B 点、参数白名单、Stop 前后证据 |
| 硬件生 3：视觉与标定 | H-03；RGB-D/YOLO、手眼标定、base 坐标 | 三条非空定位 JSON、标定副本/hash、误差和坐标约定 |
| 硬件生 4：评价与证据 | H-04/H-05；评价器、三阶段媒体、实验归档 | 成功/失败 `evaluation.json`、图片/视频、manifest、SHA256 |
| 硬件生 5：实验与迭代 | H-06/H-07/H-08/H-09；失败复现、单参数 P1、视频/语音 | `p0_experiment_id`、候选参数 ACK、`comparison.json`、同条件说明 |

主责人之间的依赖顺序是：硬件生 1/2 先打通安全 bridge → 硬件生 3 提供定位 → 硬件生 4 提供评价与证据 → 硬件生 5 才能做 P1；没有前一环的可复验输出，后一环不能用口头结果替代。

详细接口定义见：[ArmPi Bridge 中文接口合同](../roboscientist/hardware_bridge/BACKEND_CONTRACT_CN.md)。
