# 硬件侧下一步任务书：厂商视觉-语言-动作闭环与接口化交付

> 日期：2026-07-23
>
> 项目：RoboScientist 机械臂 AI Scientist
>
> 当前背景：硬件侧已初步验证真实机械臂运动闭环，包括 `move_to_pose()`、IK 求解、舵机映射、真实运动、末端位姿反馈、夹爪开合、回零与软件停止。下一步需要验证并封装机械臂自带视觉/大模型/VLA 能力，为上层 AI Scientist 提供可调用的实验执行底座。

## 1. 阶段目标

本阶段目标不是证明“厂商自带功能能演示一次”，而是把厂商自带视觉、大模型或 VLA 能力整理成上层软件可调用、可记录、可复验的接口。

目标闭环为：

```text
语言/文本指令
  -> 场景采集
  -> 目标识别
  -> 目标位姿获取
  -> camera 坐标转 base 坐标
  -> 抓取/放置动作规划
  -> 机械臂执行
  -> 返回结构化结果、日志、图像、状态和失败原因
```

首版任务固定为：

```text
抓取指定颜色方块，并放到固定目标区域。
```

优先颜色：

- 红色方块；
- 蓝色方块；
- 绿色方块。

## 2. 本阶段定位

厂商自带视觉/大模型/VLA 能力在本项目中定位为：

```text
baseline / 执行底座 / 感知与动作能力来源
```

团队作品的核心创新仍然是：

```text
任务规划
  -> 实验执行
  -> 数据获取
  -> 失败分析
  -> 参数或 Skill 更新
  -> 重复验证
  -> 晋升/拒绝/回滚
```

因此硬件侧必须明确区分：

| 类型 | 说明 |
|---|---|
| 厂商已有能力 | 视觉识别、VLA 示例、语音/大模型示例、颜色抓取示例、运动学、底层控制 |
| 硬件组本阶段工作 | 跑通、验证、封装、记录、接口化、整理限制与证据 |
| 软件侧原创工作 | AI Scientist 规划、反馈迭代、实验数据分析、Skill 版本管理、前端/API |

不得把“厂商自带 VLA 一次性执行成功”写成团队自进化能力。它只能作为真实执行数据来源。

## 3. 当前已知事实

来自 `ArmPi_Ultra_motion_closed_loop_implementation_record.docx`：

- `get_robot_state()` 已验证真实舵机反馈；
- `move_joints()` 已验证关节运动；
- `open_gripper()` 已验证夹爪打开，当前测试值：Servo ID1 -> 400；
- `close_gripper()` 已验证夹爪闭合，当前测试值：Servo ID1 -> 600；
- `stop()` 已验证软件停止命令；
- `reset_home()` 已验证可回初始姿态；
- `get_end_effector_pose()` 已验证末端位姿反馈；
- `move_to_pose()` 已完成真实运动闭环验证。

关键舵机映射：

```text
Servo ID1：夹爪
Servo ID2-ID6：机械臂运动关节

IK pulse[0] -> Servo ID6
IK pulse[1] -> Servo ID5
IK pulse[2] -> Servo ID4
IK pulse[3] -> Servo ID3
IK pulse[4] -> Servo ID2
```

已验证测试点：

```json
{
  "x": 0.0,
  "y": 0.10,
  "z": 0.30,
  "pitch": -90.0,
  "speed": 8.0
}
```

示例结果：

```text
IK success: True
IK pulse: [125, 863, 622, 134, 504]
Final end-effector pose:
x ≈ 0
y ≈ 0.100010
z ≈ 0.300106
```

这些事实说明：运动控制链路已具备接入 `RealArmAdapter` 的初步基础。但视觉识别、坐标转换、抓取判定和 VLA 闭环仍未完成。

## 4. 本阶段必须回答的问题

硬件侧需要用实机证据回答以下问题：

1. 厂商自带视觉模块能否被 Python/ROS2 程序调用，而不是只能通过 GUI 点击？
2. 厂商自带大模型/VLA/语音模块是否存在？实际入口是什么？
3. 能否输入文本指令，例如“抓取红色方块并放到目标区域”？
4. 能否获取目标识别结果，包括 label、confidence、bbox、深度或三维坐标？
5. 能否得到 `camera -> base` 坐标转换后的机械臂目标位姿？
6. 能否调用现有 `move_to_pose()` 和夹爪动作完成抓取/放置？
7. 能否返回结构化 JSON 结果？
8. 能否保存每次实验的图像、深度图、日志、视频、舵机状态和末端位姿？
9. 失败时能否区分原因：未识别、低置信度、深度无效、坐标转换失败、IK 失败、抓取失败、放置失败、超时、人工停止？
10. 连续运行 5-10 次后，成功率、失败原因和数据完整性如何？

## 7. 分工

### A：接口与 ROS2 / 厂商模块调查

负责事项：

- 调查厂商自带视觉、大模型、语音、VLA 示例是否存在；
- 找到启动命令、脚本路径、launch 文件、依赖环境；
- 确认是否能通过 Python/ROS2 程序调用；
- 整理 ROS2 node/topic/service/action；
- 封装 `run_vla_task()` 的外层入口；
- 与软件侧对齐统一 JSON 输出。

必须交付：

- `01_厂商VLA能力调查.md`
- `05_VLA闭环接口契约.md`
- `ros2_node_list.txt`
- `ros2_topic_list.txt`
- `ros2_service_list.txt`
- `ros2_action_list.txt`
- 至少一个可运行入口脚本或命令。

验收标准：

- 非 A 成员按文档能启动厂商相关模块；
- 能说明哪些能力来自厂商，哪些是本阶段封装；
- 能返回结构化 JSON，而不是只展示 GUI。

### B：动作执行、安全边界与恢复

负责事项：

- 基于已验证的 `move_to_pose()` 完成抓取动作链；
- 确认安全工作空间；
- 确认速度、pitch、z 高度、夹爪参数范围；
- 验证 `stop()`、`reset_home()`、物理急停、恢复流程；
- 定义不可执行条件。

必须交付：

- `04_动作执行与安全边界.md`
- `safety_profile_v0.json`
- `motion_test_records.csv`
- 越界/超时/停止样例 JSON。

验收标准：

- 动作执行前有安全检查；
- 越界或低置信度目标不会执行；
- 停止后不会自动继续动作；
- 至少连续 10 次安全基础动作无未解释异常。

### C：视觉识别与结果判定

负责事项：

- 跑通相机采集；
- 跑通颜色方块识别；
- 输出目标 label、confidence、bbox、camera_pose；
- 保存 RGB/深度图；
- 定义抓取、提起、放置是否成功的视觉或状态判据；
- 收集失败样例。

必须交付：

- `02_视觉接口与目标识别输出.md`
- `detections_sample.json`
- RGB/深度样例图；
- 目标缺失、低置信度、深度无效样例。

验收标准：

- 能识别红/蓝/绿至少一种颜色方块；
- 每个检测结果必须有置信度和证据图片；
- 目标不可见或置信度低时返回失败原因，而不是继续执行上一次坐标。

### D：标定与坐标转换

负责事项：

- 确认 `camera`、`base`、`tool`、`table` 坐标系；
- 整理相机到机械臂基座坐标转换；
- 记录标定流程、参数文件、版本；
- 计算静止目标重复定位误差；
- 给出可执行误差范围和拒绝阈值建议。

必须交付：

- `03_camera_to_base坐标转换.md`
- `calibration_v0.json`
- `base_pose_sample.json`
- `定位误差报告-v0.md`

验收标准：

- 任一目标位姿都必须标明 `frame_id`；
- 无有效标定版本时不得执行真实抓取；
- 至少 10 次静止目标重复测量，输出均值、标准差、P95。

### E：闭环实验、数据归档与复盘

负责事项：

- 设计实验 ID；
- 组织 5-10 次完整 VLA 闭环实验；
- 保存每次实验的输入、图像、日志、视频、结果；
- 统计成功率、失败原因、数据完整率；
- 汇总可用于软件侧调试的样例包。

必须交付：

- `06_闭环实验记录与复盘.md`
- `experiment_index.csv`
- 每次实验的 `manifest.json`
- 每次实验的 `result.json`
- 视频或录屏路径；
- 失败样本索引。

验收标准：

- 每次实验都有唯一 `experiment_id`；
- 成功、失败、拒绝、人工停止都必须保存；
- 失败样本不得删除；
- 软件侧可以直接读取样例 JSON 做接口开发。

## 8. 推荐时间安排

建议以 5 天为一个小阶段推进。

| 日期 | 目标 | 必须产出 |
|---|---|---|
| Day 1 | 厂商 VLA/视觉/大模型能力调查 | 启动命令、脚本路径、ROS2 接口清单、能否程序调用结论 |
| Day 2 | 视觉采集与目标识别 | RGB/深度样例、目标检测 JSON、低置信度/失败样例 |
| Day 3 | 坐标转换与动作执行打通 | camera_pose -> base_pose -> move_to_pose -> gripper 动作记录 |
| Day 4 | 完整 VLA 闭环首跑 | 一条命令或脚本完成“指令 -> 识别 -> 抓取/放置 -> 返回结果” |
| Day 5 | 重复实验与交付整理 | 5-10 次实验记录、成功率、失败原因、接口契约文档 |

如果 Day 4 前无法跑通厂商 VLA，不要卡住，应改为：

```text
厂商视觉识别 + 我们封装的确定性动作执行
```

即先实现：

```text
文本指令解析颜色
  -> 厂商视觉识别颜色方块
  -> camera_to_base
  -> move_to_pose + gripper
  -> 返回结构化结果
```

这样仍然能为软件侧提供真实感知与动作数据。

## 10. 错误码建议

硬件侧返回结果中建议使用以下错误码，便于软件侧做失败分析：

| 错误码 | 含义 |
|---|---|
| `VENDOR_VLA_UNAVAILABLE` | 厂商 VLA/大模型模块不可用 |
| `CAMERA_UNAVAILABLE` | 相机不可用 |
| `OBJECT_NOT_FOUND` | 未检测到目标 |
| `LOW_CONFIDENCE` | 目标置信度低 |
| `DEPTH_INVALID` | 深度无效 |
| `CALIBRATION_MISSING` | 缺少有效标定 |
| `TRANSFORM_FAILED` | 坐标转换失败 |
| `OUT_OF_WORKSPACE` | 目标位姿越出安全空间 |
| `IK_FAILED` | 逆运动学求解失败 |
| `MOTION_TIMEOUT` | 运动超时 |
| `GRASP_FAILED` | 抓取失败 |
| `PLACE_FAILED` | 放置失败 |
| `STOPPED_BY_OPERATOR` | 人工停止 |
| `UNKNOWN_ERROR` | 未分类异常 |

## 13. 对软件开发的影响

如果本阶段通过，软件侧可以开始把 `RealArmAdapter` 从 stub 升级为第一版真实适配器。

建议接入顺序：

```text
第一步：读取硬件侧样例 JSON，完成离线 replay
第二步：调用 run_vla_task()，完成真实单轮任务
第三步：把结果写入 ExperimentResult
第四步：进行失败分析和候选 Skill 生成
第五步：先人工确认，再允许第二轮真实执行
```

注意：即使厂商 VLA 能一次执行成功，软件侧也不能让 LLM 直接控制舵机或 ROS2 底层 topic。真实执行必须通过 `RealArmAdapter`，并经过安全检查。

## 14. 不能做的事

- 不能只交 GUI 截图；
- 不能只说“跑通了”，必须有命令、代码、日志、JSON 和视频；
- 不能把厂商能力写成团队原创能力；
- 不能把一次成功当作稳定能力；
- 不能删除失败样本；
- 不能用上一帧目标坐标代替当前识别结果；
- 不能在无有效标定时自动执行真实抓取；
- 不能让上层软件直接接触舵机 ID、pulse 或底层 ROS2 topic。

## 15. 阶段结论口径

本阶段如果完成，正确表述应为：

> 硬件侧已基于 ArmPi Ultra 厂商视觉/语言/动作能力，完成固定颜色方块场景下的一次 VLA 执行底座验证，并将其封装为可供 AI Scientist 调用的结构化接口。该能力为后续“实验规划—执行—数据分析—反馈迭代”提供真实实验数据来源。

不应表述为：

> 我们已经完成机械臂自进化智能体。

自进化能力必须由软件侧基于多轮实验结果、失败分析、参数或 Skill 更新、重复验证和版本晋升/回滚来证明。
