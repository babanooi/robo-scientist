## 1. 项目一句话

本项目是面向挑战杯赛道一方向一 B 的“机械臂 AI Scientist”：用户通过文本或语音下达颜色方块抓取任务，系统生成实验计划，调用 ArmPi Ultra 执行，记录实验结果，再根据失败证据调整下一轮参数或 Skill，并通过重复实验决定晋升或回滚。

答辩主线不是“语音控制机械臂”，也不是“机械臂能抓东西”，而是：

```text
任务规划 -> 安全执行 -> 数据记录 -> 失败分析 -> 参数/Skill 更新 -> 重复验证 -> 晋升/回滚
```

## 3. 当前已确认事实

### 3.1 产品与比赛方向

- 赛题方向：赛道一，方向一 B，科学实验任务规划与反馈迭代。
- MVP 场景：固定场景下抓取指定颜色方块并放到目标区域。
- 核心创新：不是厂商已有识别/抓取能力，而是 AI 根据实验结果调整下一轮计划，并逐步提升抓取率、任务完成率或路径/耗时指标。
- 安全原则：LLM 不能直接输出舵机脉冲或绕过安全层；所有运动必须经过确定性安全检查。

### 3.2 最新硬件进展

研究生已经跑通了第一条程序化控制链路：

```text
Python -> ROS2 -> 舵机 Topic/Service -> 夹爪开合/舵机状态读取 -> home.json -> Windows 下载保存
```

已验证内容：

| 项目 | 当前结论 |
|---|---|
| 机械臂 IP | `192.168.149.1` |
| 控制 Topic | `/ros_robot_controller/bus_servo/set_position` |
| 状态 Service | `/ros_robot_controller/bus_servo/get_state` |
| 消息类型 | `ros_robot_controller_msgs/msg/ServosPosition` |
| 服务类型 | `ros_robot_controller_msgs/srv/GetBusServoState` |
| 夹爪舵机 | Servo ID `1` |
| 夹爪打开测试值 | `position = 400` |
| 夹爪闭合测试值 | `position = 600` |
| 状态读取 | 可逐个读取 Servo 1-6 的 `position` |
| 保存文件 | 树莓派 `~/my_armpi/home.json` |
| Windows 下载 | 通过临时 HTTP 服务下载 `home.json` 到 `records/robot_state_*.json` |
| 已有脚本 | `robot_control.py`、`home_control.py`、`download_home.py` |

这个进展可以写入 PRD，表述为：

> 当前已完成夹爪控制与舵机状态读取的最小程序化验证，证明上层软件可以不依赖 GUI，通过 ROS2/Python 与机械臂底层能力建立连接。

但它还不能证明完整抓取闭环。当前仍未验证：主体关节安全运动、目标识别、三维坐标、相机到基座坐标转换、抓取成功判定、批量实验归档。

## 4. 周末你的主要任务

周末优先完成 PRD v1，不要等硬件组把全部实机数据补齐。PRD 要把“已验证事实”和“待验证假设”分层写清楚。

### 4.1 PRD v1 必须包含

1. 项目背景与赛题适配  
   说明为什么这是“科学实验任务规划与反馈迭代”，不是普通机械臂 Demo。

2. 用户目标与演示任务  
   固定场景下，用户输入“抓取红色方块并放到目标区”，系统执行并记录结果。

3. 产品闭环  
   任务输入、实验计划、安全检查、执行、记录、评估、失败分析、参数更新、重复验证、晋升/回滚。

4. 系统架构  
   上层智能体、本地 Mock、实机适配器、硬件 ROS2/SDK、视觉/标定、安全层、数据层、前端看板。

5. MVP 范围  
   必须做什么，不做什么。语音可以作为增强，不是核心。

6. 数据 Schema 初稿  
   至少定义 `ExperimentPlan`、`ExperimentResult`、`RobotActionResult`、`ObjectPose`、`SkillVersion`。

7. 安全边界  
   明确 LLM 不直接控制舵机；所有动作由确定性代码检查工作空间、速度、超时、置信度和场景状态。

8. 评估指标  
   任务完成率、抓取成功率、放置成功率、定位误差、耗时、路径长度、安全事件数、回滚次数。

9. 硬件依赖与风险  
   把已跑通夹爪/状态读取列为事实；把视觉、标定、完整抓取列为待验证。

10. 阶段验收标准  
    P0 夹爪与状态读取、P1 Mock 闭环、P2 真实单轮、P3 重复优化、P4 演示冻结。

### 4.2 周末 PRD 成功标准

PRD v1 完成后，应能回答四个问题：

```text
1. 我们到底做什么，不做什么？
2. 厂商已有能力和团队创新点如何区分？
3. 上层软件需要硬件交付哪些结构化接口？
4. 即使硬件进展慢，软件如何先用 Mock 做出闭环？
```

如果这四个问题答不清，PRD 还不够。

## 5. 硬件组下一步必须补的数据

现在硬件组不需要继续泛泛查资料，应该围绕“实机证据”补数据。

### 5.1 夹爪与状态读取证据包

让 A 先补齐：

| 需要补充 | 验收标准 |
|---|---|
| 三个脚本原文件 | 提供 `robot_control.py`、`home_control.py`、`download_home.py` |
| 原始终端日志 | 至少一次启动 SDK、夹爪开、夹爪关、读取 1-6 舵机、保存 `home.json`、Windows 下载全过程 |
| 真实 JSON 样例 | 提供 `home.json` 和 Windows 下载后的 `robot_state_*.json` |
| 运行视频/照片 | 能证明夹爪动作真实发生 |
| 参数表 | 打开值、闭合值、推荐抓方块值、`duration`、连续开合稳定性 |
| 异常测试 | SDK 未启动、position 越界、读取超时、home.json 缺字段时的表现 |

### 5.2 主体运动最小验证

夹爪跑通后，不要直接做完整抓取。下一步是低速、小幅度验证一个非夹爪舵机或一个安全 Home 复位动作。

需要证明：

```text
输入安全小动作 -> 程序发 ROS2 指令 -> 机械臂主体移动 -> 读取最终舵机状态 -> 保存日志
```

### 5.3 视觉与坐标数据

让 C/D 补：

| 数据 | 用途 |
|---|---|
| RGB 图像样本 | PRD 中确认视觉输入 |
| 深度图/点云样本 | 判断是否能做三维抓取 |
| 颜色方块检测输出 | 定义 `ObjectPose` |
| `camera_pose -> base_pose` 样例 | 让上层能生成机械臂目标位姿 |
| 10 次重复定位误差 | 支撑后续优化指标 |

### 5.4 安全与实验归档

让 B/E 补：

| 数据 | 用途 |
|---|---|
| 工作台尺寸、桌面高度、目标区位置 | 固定场景配置 |
| 预抓取高度、速度、超时初值 | 安全层参数 |
| 急停/停止/恢复流程 | 异常处理 |
| 实验 ID 规则 | 数据可追溯 |
| 实验目录结构 | 后端日志与报告生成 |

## 7. 当前不要做的事

- 不要把 GUI 按钮可用写成“上层软件接口已完整可用”。
- 不要写“机械臂已实现自主抓取优化”，当前还没有。
- 不要把 `/kinematics/*` 当作真实执行接口，之前资料已说明它主要是求解，不等于运动。
- 不要让 LLM 直接生成舵机 ID、脉冲值和 duration 作为最终控制方案。
- 不要等硬件全部完成才写 PRD；PRD 可以先用“事实/假设/待验证”分层推进。

## 8. 换电脑后建议工作顺序

1. 打开本文件，恢复上下文。
2. 阅读 `docs/挑战杯.md` 的项目定义和架构。

5. 先写产品目标、MVP、闭环流程、架构和验收标准。
6. 再把硬件事实写入“当前验证状态”。
7. 把缺口写入“硬件待补证据”，不要强行补成已完成。
8. 最后检查 PRD 是否能指导软件开发和硬件交付。
