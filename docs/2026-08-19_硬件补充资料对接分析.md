# ArmPi Ultra 硬件补充资料对接分析

日期：2026-08-19

## 结论

最新资料已经证明红色长方体场景存在一条可用的实物基线：RGB 轮廓、注册点云深度、相机到机器人坐标变换、厂家标定、最终 TCP 残差、自动腕部方向、IK 检查和 A 到 B 动作链均已有代码和一次实物成功记录。

这解决了“上层系统能否调用一条真实抓取链”的问题，但还没有解决“系统能否机器判定每轮实验结果”和“候选 Skill 参数能否真正改变下一轮实机动作”。因此目前可接入真实 P0，不可宣称已完成实机自主反馈迭代。

## 已完成的软件接入

仓库新增 `armpi_final_wrapper_backend.py`，行为如下：

1. 真实执行前调用最终 wrapper 的 `check`。
2. 同时看到 `numeric_safety_passed` 和 `preflight_passed` 才批准。
3. 校验请求的固定 B 点、工作空间、标定字段和真实设备放行开关。
4. 执行 `pick-place` 并保留 check、执行日志和本轮发现的数据文件路径。
5. 从 `joint_states_session.csv` 计算持续时间、轨迹点数、关节总行程和派生最大关节速度。
6. 指标名称使用 `joint_total_travel_rad`，不伪装成米制 TCP 路径长度。
7. 未配置结果评估器时，即使动作链完成也返回 `HARDWARE_UNVERIFIED`。
8. 未配置真实软件停止命令时拒绝实机执行。

旧 `armpi_backend.py` 仍保留，用于确实存在 `/home/ubuntu/my_armpi` 高层函数模块的环境；它不是最新红色长方体基线的默认入口。

## 当前无法宣称的能力

- 不能宣称数据包中的 10 条目标事件等于 10 次成功抓取。
- 不能宣称当前 CSV 提供了力矩、接触力或真实 TCP 路径。
- 不能宣称上层生成的 `grasp_offset_m`、`transit_height_m` 已作用到最终 wrapper。
- 不能把固定动作模板的重复执行描述为路径规划器自主优化。
- 不能用 Mock、dry-run 或人工未确认的动作完成状态计算抓取成功率。

## 硬件侧仍需交付的三个阻塞项

### H1 软件停止接口

交付当前设备上已实测的最快安全停止命令或高层函数，并说明调用条件、返回值、失败行为。软件侧通过 `ARMPI_STOP_COMMAND` 配置。验收标准：运动中调用 `POST /stop`，机械臂按硬件负责人批准的方式停止，接口返回结构化结果。

### H2 结果评估接口

至少先提供人工确认结果的结构化记录，后续再升级为视觉自动判定。每轮必须区分：

```json
{
  "object_grasped": true,
  "object_lifted": true,
  "object_placed": true,
  "position_error_m": 0.004,
  "evidence": ["before.jpg", "lift.jpg", "after.jpg"]
}
```

验收标准：结果能够对应唯一 `experiment_id`，有原始证据路径，未知值不能默认为 true。

### H3 候选参数执行接口

最终 wrapper 当前只有 `check|pick-place`，没有证据表明它会读取上层候选参数。硬件侧需要选择一个最小参数族并打通，例如“受限抓取偏移”或“受限中转高度”，输入必须经过白名单和数值范围校验。

验收标准：P0 和 P1 的输入 JSON、wrapper 日志和实机动作证据能证明同一个参数发生了受控变化；越界值在运动前被拒绝；不能通过 LLM 直接下发舵机 ID、脉冲或 ROS2 底层 topic。

## 下一次实机验证成功标准

1. `/health` 返回 `real_motion`、`available=true`、`stop_available=true`。
2. P0 的 check 日志同时包含两个放行状态。
3. P0 执行包包含 wrapper 日志、最新目标和关节 CSV。
4. 现场人员对抓住、提起、运输未掉落、B 点放置逐项确认并留下图像或视频证据。
5. 若未完成 H3，只验收真实 P0 接入，不运行或宣传 P1 实机优化。
