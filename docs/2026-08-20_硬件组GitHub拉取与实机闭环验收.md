### 0.3 现场执行顺序

1. A 在 ArmPi 主机完成拉取和依赖安装，先运行第 3 节只读能力采集器；E 把生成的 `.tar.gz` 原样回传软件侧。此步不运行任何 `check` 或 `pick-place`。
2. 软件侧根据能力包确认真实源码字段和入口，再给出或审核参数化 wrapper 映射；没有完成该审查前，不凭手册猜测 JSON 字段或改动冻结脚本。
3. A 完成 profile 审核、bridge 启动和软件停止实测；B/D 联合确认运动/标定配置。
4. A 在**不执行 `pick-place`**的前提下运行本页第 8 节的 `verify_hardware_setup.py --require-closed-loop`，E 保存完整输出。未显示 `ready for supervised P0` 时停止，不进入动作阶段。
5. B 现场监护，先执行 P0 `check`，再执行一次 P0。C 写 `vision` 评估，D 只根据其结构化证据给出残差或不可归因结论，E 封存 P0 目录。
6. 只有 P0 构成可归因失败时才生成候选 P1；该候选只变更一个参数族。B 审批后，参数化 wrapper 必须对 P1 的 `check` 与 `pick-place` 都读取参数文件并回显同一个 SHA256。
7. B 现场监护 P1，C 重新评估，E 封存 P1 目录。对照本页第 10 节逐项审计，结果只能是“候选验证完成/拒绝/受阻”，不能以单次 P1 宣称晋升或成功率提高。

## 0.4 软件接口和运行模式（现场拉取后必须复核）

硬件组只使用记录在实际提交中的接口，不自行改字段名。拉取后先执行：

```sh
curl -fsS http://127.0.0.1:8001/api/config
```

成功标准是返回 JSON，且不包含 `DASHSCOPE_API_KEY` 的值。保存完整响应，核对
Qwen 配置状态、模型名、`real_arm` 是否需要 profile 和允许的 campaign 字段。
若路由不存在、响应不是 JSON 或字段与下表不一致，停止实机动作并把提交哈希和响应回传软件侧。

| 模式 | 请求字段 | 可用于什么 | 是否能形成赛题 Qwen 证据 |
|---|---|---|---|
| `qwen_required` | `use_qwen: true`（官方路径，默认） | Qwen 规划、结果解释和受确定性安全层约束的 P0→P1 | 可以，前提是两次真实调用的证据包完整 |
| `deterministic_only` | 必须显式 `use_qwen: false` | 无网络的 API、桥接、视觉和安全合同检查 | 不可以，只能做联调/预演 |

Qwen 进程环境变量如下，API Key 只注入进程环境，不写入代码或实验包：

```sh
export DASHSCOPE_API_KEY='REDACTED_AT_HANDOFF'
export DASHSCOPE_BASE_URL='https://dashscope.aliyuncs.com/compatible-mode/v1'
export QWEN_MODEL='qwen3.7-plus'
export QWEN_TIMEOUT_S='90'
```

确认账户确实能访问所选模型；`qwen3.7-plus` 只是当前默认值，不是现场权限证明。Qwen 缺少 Key、调用失败或 Schema 校验失败时，`use_qwen: true` 必须返回结构化错误并停止，不得自动降级为 `deterministic_only`。

活动请求（现场服务地址和固定场景可按部署替换）为：

```sh
curl -fsS -X POST http://127.0.0.1:8001/api/campaigns \
  -H 'Content-Type: application/json' \
  -d '{
    "task_text": "把固定工作台上的红色方块放到右侧目标区域",
    "scenario": "pose_offset",
    "mode": "real_arm",
    "use_qwen": true,
    "auto_run_p1": true
  }'
```

响应中的 `campaign_id` 必须能由下列请求完整取回，不得只截取网页文字：

```sh
curl -fsS http://127.0.0.1:8001/api/campaigns/<campaign_id>
```

现场必须保留返回的 P0/P1 实验 ID、`data_source`、Qwen 调用元数据和结构化错误。`auto_run_p1` 只是允许软件在所有自主门通过后继续候选验证，不能取消现场监护、软件停止或人工接管。

## 1. 本次验收究竟证明什么

完整验收链是：

```text
P0 计划
→ wrapper check 安全门
→ 实机动作
→ 视觉结果评估
→ 带符号的失败残差
→ 只修改一个参数族的候选 P1
→ 参数 wrapper 确认实际应用
→ P1 实机复验
→ P0/P1 证据包对比
```

以下情况只能算“实机接入”，不能算“自主反馈迭代”：

- 只看到 `pick_place_sequence_completed`；
- 由人看完后口头说成功，但没有结构化结果文件；
- 上层生成了 P1，但实机 wrapper 没有读取候选参数；
- P0 和 P1 使用了同一套固定动作参数；
- 只有单次 P1 成功，就直接宣称 Skill 已进化或晋升。

## 7. 实现参数化 P1 wrapper

仓库已提供 `armpi_parameterized_runner.py`。硬件侧只需实现：

```text
/home/ubuntu/armpi_tasks/run_roboscientist_experiment.sh
```

调用合同：

```sh
bash run_roboscientist_experiment.sh check \
  --parameters <本轮skill_parameters.json> \
  --parameters-sha256 <64位sha256>

bash run_roboscientist_experiment.sh pick-place \
  --parameters <本轮skill_parameters.json> \
  --parameters-sha256 <64位sha256>
```

wrapper 必须读取 JSON，把其中参数映射到已审核的高层运动函数，并在映射完成后原样输出：

```text
STATUS: skill_parameters_applied sha256=<同一个64位sha256>
```

`check` 还必须输出两个安全状态，`pick-place` 完成动作链后输出 sequence 状态。只打印 SHA256 但不真正使用参数属于验收失败。

当前允许的参数范围：

| 参数 | 允许范围 |
|---|---|
| `grasp_offset_m[x,y,z]` | 每轴绝对值不超过 0.020 m |
| `approach_height_m` | 0.01–0.10 m |
| `transit_height_m` | 0.05–0.20 m |
| `speed_m_s` | 0.02–0.15 m/s |

上层候选必须只改变一个参数族。当前候选族为 `grasp_offset` 或 `path_profile`；速度和 approach 不参与自动调整。

配置：

```sh
export ARMPI_PARAMETERIZED_WRAPPER=/home/ubuntu/armpi_tasks/run_roboscientist_experiment.sh
export ARMPI_EXPERIMENT_RUNNER=armpi_parameterized_runner:run_experiment
```

### 7.1 资料包中的高层映射线索

此前交付的 ArmPi 资料包中，`pick_and_place.py` 暴露了
`pick_without_back(position, ...)`、`pick(position, ...)` 和
`place(position, ...)`；资料同时明确红色长方体链路使用米制 `position`，经
厂家标定和 IK 后才进入舵机执行。它们可以作为 wrapper 的调查起点，但不是对
当前设备源码路径或初始化方式的替代确认。

实现 `grasp_offset` 时，必须遵守以下顺序：

1. 继续运行与 P0 完全相同的动态识别、深度/像素/运动学标定和安全检查；
2. 在已审核的 `base` 坐标系目标进入 IK 之前，对 `position[0:3]` 应用候选的
   `grasp_offset_m` 一次；
3. 记录偏移应用前后的米制坐标、坐标系、参数 SHA256 和实际调用的高层函数；
4. 不在 `set_servo_position`、舵机 ID、脉冲值或 ROS 2 底层 topic 层再次叠加偏移；
5. 保留红色长方体成功基线要求的 `--pick-radial-trim 0.000`，不得把历史
   `-0.040 m` 修正与候选偏移叠加。

`approach_height_m`、`transit_height_m` 和 `speed_m_s` 只有在硬件侧确认高层
函数确实接受并使用它们时才能接入；不能因为参数出现在 JSON 中就宣称已生效。
若现场选择在 `apply_final_tcp.py` 或最终目标脚本中实现偏移，必须在映射说明中
注明“唯一生效层”，并用 P0/P1 日志证明没有重复校正。


Web 服务终端还需单独导出 Qwen 配置。它不需要重复导出 bridge 内部的
`ARMPI_*` 变量，但必须能访问 profile 中的 bridge URL。

打开 `http://<机械臂IP>:8001`。选择“真实机械臂”。顶部四项应显示桥接、停止、结果评估、候选参数均就绪。

先运行 P0。官方演示通过 campaign API 使用 `use_qwen: true`、`auto_run_p1: true`；

## 10. 实机闭环通过标准

必须同时满足：

1. P0 和 P1 的 `data_source` 均为 `real_arm`，且响应可由 `GET /api/campaigns/<campaign_id>` 完整回取。
2. P0 和 P1 使用同一 `scene_id`、目标/放置位姿、标定版本、光照/相机条件、评价器版本和成功判据；不得通过切换场景制造改善。
3. P0 和 P1 都来自 `evaluator_type=vision`，使用同一个非空 `evaluator_version`，并各自有独立 `evaluation_file` 和图像/视频证据；`operator` 或 `hybrid` 只能进入人工复核，不得形成自主闭环分类。
4. P0 失败包含结构化失败码；位置补偿必须包含带符号 XYZ 残差。
5. P1 相对 P0 只改变一个允许的参数族，并由 Qwen 调整意见和确定性优化器共同留痕；Qwen 不能直接输出底层舵机/ROS 指令。
6. P1 `check` 和 `pick-place` 日志都包含与参数文件一致的 SHA256 回显，且 wrapper 返回的 `executed_parameters` 与请求完全一致；仅打印摘要不合格。
7. P1 的 `artifacts.execution_profile` 为 `parameterized_red_cuboid_runner_v1`。
8. P1 再次经过工作空间、速度、偏移、wrapper check 和 IK 安全门，且不绕过 `ROBO_ALLOW_REAL_ARM=1`、停止命令或桥接健康检查。
9. P1 结果再次由视觉评估器产生，不使用 P0 结果或人工口头结论；Qwen 调用失败、策略与确定性允许族不一致或请求被安全层拒绝时不得运行 P1。
10. `data/real-arm-test/experiments/` 同时保留两轮 plan/result/analysis、视觉工件、wrapper 日志和 Qwen 元数据，不覆盖旧实验。
11. P1 仍为 candidate。至少 10 次独立验证前不得晋升或宣传成功率提升；这 10 次是本项目内部建议，不是官方固定数字。
